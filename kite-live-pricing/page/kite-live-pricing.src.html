Kite · storefront pricing · working prototype

Run Kite's discount function in the browser, and let any page price itself

Shopify only runs a discount function once items are in the cart. Today Kite fills the gap with a hand-written JavaScript copy of the Rust logic, and the two drift apart. This page tests a different idea: compile the same function to WebAssembly once, then run that file both in Shopify and in the shopper's browser. Every price, nudge and tier below comes from Kite's real custom-discount-builder function, built from the app7 repo and running on this page.

      How it works
      
One discount function, run in two places

      
A Shopify discount function takes a JSON description of a cart and returns JSON discounts. It doesn't touch the network or any other state, so the same compiled file gives the same answer wherever it runs. Kite's functions use shopify_function 0.8, which reads its input on stdin and writes its result on stdout. A browser can provide those six system calls in about 60 lines of JavaScript. That is all the "runtime" on this page is.

      

        

          
Kite adminMerchant saves an offer. Kite builds the function config (the metafieldInfo JSON).

        

        →
        

          
ShopifyConfig goes on the discount metafield. The .wasm is deployed with the app. Runs at cart and checkout.

          
Storefront (new)The same config is published as an offer contract. The same .wasm is served from Kite's CDN.

        

        →
        

          
Kite.quoteBuilds the function input from any hypothetical cart, runs the function, turns its output into prices and messages.

          
Any UIBundle builders, product page tables, cart bars, headless sites, or an AI agent writing theme code.

        

      

      
The function returns discounts and a message, nothing else. Everything a shopper-facing page needs beyond that, such as "add 1 more to get 15% off" or "this item would cost $21.60", comes from asking the function what-if questions. The engine re-runs it on the cart plus one more item, then plus two, and reports the first change. Each run takes well under a millisecond once loaded. A whole update on this page, often 60 or more runs, finishes in a few milliseconds. Because the rules live inside the function, this works the same way for tiers, buy-X-get-Y, set pricing, and any rule type Kite adds later. Nobody re-implements the rules in JavaScript.

Recommendation: use the in-browser function for every interaction. Keep /cart.js as the source of truth once items are in the cart. A throwaway Storefront API cart is an optional "confirm" step for headless storefronts or high-value bundles. Tokenless Storefront API access covers cart reads and writes from a theme. Shopify has no dedicated preview or dry-run endpoint.

Every function input field has a storefront source

      
The function's input query (generate_cart_run.graphql) is the full list of what it can see. Each field can be filled on a theme without asking Shopify anything:

      

        

          
Function inputWhere the storefront gets it

      What a merchant's agent writes
      
The bundle page above, in about 20 lines

      
This is the whole integration surface. An agent reading a one-page llms.txt could produce it without knowing Kite's internals:


<script type="module">
  await Kite.ready;                                   // loads the offers + function .wasm once
  const offer = Kite.offers({ collection: 'routine' })[0];

  async function render(selection) {                  // selection: [{ variantId, quantity }]
    const q = await Kite.quote({ lines: selection });  // runs Kite's discount function locally
    for (const line of q.lines) {
      priceEl(line.variantId).innerHTML = line.finalPrice < line.price
        ? `<s>${money(line.price)}</s> ${money(line.finalPrice)}` : money(line.price);
    }
    nudgeEl.textContent = q.next
      ? `Add ${q.next.remaining} more to get ${q.next.message}`   // found by what-if runs
      : q.applied.map(a => a.message).join(' · ');
    totalEl.textContent = money(q.total);
    badgeEl.dataset.state = q.confidence;              // 'predicted' until Shopify confirms
  }

  addBtn.onclick = () => Kite.addToCart(selection, { offerId: offer.id });
  // stamps the line properties the function needs, then checks /cart.js and fires
  // Kite.on('update') if Shopify's real price differs from the prediction
</script>

      
The API names are a proposal. The demo on this page implements quote, the what-if nudges, and the add-to-cart properties. Kite.ready, offers, on and the reconcile step are not built yet.

    


    

      What it takes
      
Build order

      
    
        
  1. Publish the function config to the storefront.Today routes/frontend/frontend.service.js (around line 491) loads consolidated discounts with .select('-metafieldInfo …'), so the storefront never sees what the function sees. Add a sanitised copy to the payload. Replace privateCampaignValue with a hash so private campaigns stay private, and the engine compares the hash of the shopper's campaign. Headless sites need it as a metaobject or a shop metafield with storefront access, because app.metafields is only readable inside Kite's app embed.
    2. 
        
  2. Ship the same .wasm to Kite's CDN.shopify app deploy already builds each function. Upload the identical file, named by its content hash, and put the hash in the contract so the browser and Shopify always run the same build. Load it only on pages that call Kite.quote.
    3. 
        
  3. Build Kite.js.The WASI shim, one input builder per function (written from each function's .graphql query), output-to-price allocation, what-if nudges, addToCart with the required properties, and reconcile against /cart.js on Shopify's shopify:cart:lines-update event. That event's payload has no discount details, so reconcile has to re-fetch /cart.js.
    4. 
        
  4. Write agent-facing docs.An llms.txt with the contract, the four API calls, "always add through Kite.addToCart", and three worked examples.
    5. 
        
  5. Move Kite's own widgets onto it.Strikethrough, BXGY, progress bar and volume tiers call Kite.quote, and strikethrough-logic.js plus the maths in customDiscountLogic.js go away. This gives the same result as the existing remove-storefront-discount-calculation-plan.md without losing storefront prices.

      Found while building this
      
Things to know

      
    
        
  • A bad config crashes the function, it doesn't return zero. One of my test configs left out qualifierType on a rule. The function panicked (generate_cart_run.rs:1192). At checkout that means "no discount". In the browser, the engine should report "unknown" and show no price, not a $0 discount.
    • 
        
  • Line properties decide eligibility. Switch the add mode to "Theme's own /cart/add.js" on the "Any 3 for $75" offer. Without _kite_bundle on the lines, the real function returns nothing. A merchant's page that skips Kite.addToCart shows a price the shopper won't get.
    • 
        
  • "Multiply set pricing" repeats whole sets. It discounts every item in each complete set. It can't express "every 3rd item 10% off" on its own, which matters if merchants ask for repeating BXGY on custom pages.
    • 
        
  • The test fixture in the repo is stale. custom-discount-builder/input.json has no buyerIdentity.isAuthenticated, so the current function rejects it. Running functions outside Shopify would catch drift like this in CI.
    • 
        
  • Stacking is still Shopify's call. Other apps' discounts and the merchant's combination settings are invisible to any one function. The engine assumes Kite's offers don't stack with each other (best discount per line wins) and marks every price as predicted until /cart.js confirms it.
    • 
        
  • Size is in line with today. Each function is about 230 to 310 KB raw and 90 to 110 KB gzipped, before wasm-opt. The customDiscountLogic.js bundle that ships today is 122 KB minified.
    • 
      

    


    

      Decisions for the team
      
Open questions

      
    
        
  • Which surfaces first? The churned store's case (custom bundle builder, DiscountKit Live) suggests bundle pages and product-page tiers.
    • 
        
  • How public should offer rules be? app_data is already rendered into every page by the app embed, so most rules are visible today. A versioned public contract makes that a commitment.
    • 
        
  • Headless in v1? Theme-only can use the existing app embed. Headless needs the metaobject route and a hosted script.
    • 
        
  • Who owns the removal plan? This approach and remove-storefront-discount-calculation-plan.md both delete the JavaScript maths; they should become one plan.
    • 
        
  • Is DiscountKit Live the bar? From the meeting notes, it publishes a metafield and the merchant's UI does the maths. Shipping the maths too goes a step further.
